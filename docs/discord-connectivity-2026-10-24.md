# Discord: цикл подключения к голосовому каналу

Статус исправления совместимости TCP: **Experimental**, выключено по умолчанию. Voice и Go Live **Not Verified**: транспортные проверки не входят в канал и не используют пользовательские токены.

## Наблюдения

В пользовательском SOCKS5-профиле был выбран Standard вместо Docker NAT. После исправления на явную публикацию `20000–20030` появились ответы UDP: в новой записи максимум 756 отправленных и 798 полученных пакетов. Это общие счётчики профиля, включая другие приложения, а не доказательство голоса Discord. В журнале Discord остались ошибки RTCControlSocket/WebSocket; также встречались отказы UDP ASSOCIATE.

Независимая проверка двух voice-серверов через Dante без TUN дала HTTP 101 с правильным Sec-WebSocket-Accept по IPv4. SOCKS5 CONNECT к их IPv6-адресам получил REP=8. Это подтверждённая несовместимость upstream; использование именно IPv6 каждым неудачным соединением настоящего Discord не было захвачено, поэтому единственная причина пользовательского сбоя пока не доказана.

Первая попытка только с sing-box `sniff` не исправила IPv6. Исходники 1.14.3 показывают отдельное внутреннее условие OverrideDestination, которое стандартный rule action не устанавливает: [маршрутизация](https://github.com/SagerNet/sing-box/blob/v1.14.3/route/route.go), [создание action](https://github.com/SagerNet/sing-box/blob/v1.14.3/route/rule/rule_action.go). Этот вариант не используется в итоговом генераторе.

## Режим совместимости

`ProxyProfile.UseTlsServerNameForTcp` создаёт один агентский `TlsNameSocksBridge` на используемый SOCKS5-профиль. Он слушает только IPv4 loopback и требует случайную локальную авторизацию. sing-box направляет выбранный TCP в него; UDP использует прежний независимый строгий транспорт. Флаг без настоящего посредника не создаёт рабочего TCP-маршрута: preview выдаёт Reject, валидация использует инертный endpoint только для check.

Посредник читает ClientHello через TLS-парсер .NET, не выдаёт сертификат и не отправляет клиенту TLS-ответы. Все прочитанные байты передаются без изменения; сертификат реального сервера продолжает проверять приложение. Извлечение имени ограничено 300 мс и 64 KiB. Одновременно разрешено не более 128 локальных TCP-соединений; SOCKS-handshake и первоначальное подключение ограничены 10 секундами.

Только для исходного IPv6 TCP с открытым SNI запрашивается A-запись и выполняется SOCKS5 CONNECT к IPv4 **через тот же upstream**. IPv4-назначения сохраняются. Без распознанного SNI исходный адрес сохраняется; IPv6 для таких протоколов этот режим не исправляет. ECH и все варианты TLS не приняты.

Windows System DNS во время TUN не завершил контрольный lookup в установленный срок. Поэтому узкий resolver использует HTTPS DoH JSON через тот же SOCKS5, а не прямой запрос или системный fallback. Endpoint явно отображается и сохраняется как `TcpIpv4DohServer`; по умолчанию — `https://1.1.1.1/dns-query`. Требуется буквальный IPv4, HTTPS, отсутствие userinfo/query/fragment; редиректы и cookies отключены, сертификат проверяется. Поддерживается Cloudflare/Google-подобный JSON, а не любой wireformat DoH: [формат Cloudflare](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/). SOCKS5 для HttpClient поддерживается .NET: [официальное описание](https://devblogs.microsoft.com/dotnet/dotnet-6-networking-improvements/#socks-proxy-support).

Проверяются Status, Question, тип A, цепочка CNAME и принадлежность ответа имени. Циклы, неоднозначные CNAME, усечённые ответы, чужие записи и отсутствие IPv4 отклоняются. Ответ ограничен 64 KiB; до четырёх запросов одновременно, до 128 кешированных имён, срок не выше DNS TTL и 60 секунд. Отказ DNS, SOCKS5 или TLS закрывает соединение. Direct fallback отсутствует.

Это **не** перехват всех DNS приложения и не гарантия отсутствия DNS leaks: первоначальный DNS самого Discord остаётся системным. Резолвер видит запрошенные имена. Глобальные DNS, IPv6, WFP, Docker и OpenVPN не перенастраиваются.

## Включение и проверка

1. Остановить движок и закрыть старую копию PathFlux. Запустить обновлённую сборку.
2. В SOCKS5-профиле оставить Docker NAT и опубликованный диапазон. Включить «TCP через IPv4 по имени TLS (Experimental)», проверить показанный DoH JSON endpoint и сохранить.
3. Правило `Discord.exe`: TCP + UDP, нужный профиль. Экспериментальный SOCKS5 UDP должен быть включён отдельно.
4. Запустить движок, включить запись метрик и повторить подключение Discord. Сообщение TCP/SNI в состоянии показывает только число соединений/извлечённых имён/upstream и безопасный код ошибки; содержимое TLS, домены и credentials не журналируются.
5. Подтвердить реальный голос и затем выполнить [30/60-минутную приёмку](discord-acceptance.md). При повторении цикла нужны новая запись и сетевые ошибки клиента; HTTP 101 не означает успешную авторизацию или звук.

Для повторения транспортного теста используется явный режим NetworkLab:

```powershell
& $lab voice-tcp $engine $sha $targetsJson $newOutput --allow-system-tun
```

Targets JSON содержит временный список `{ "Host": "актуальный-сервер.discord.media", "Port": 443 }`, полученный из собственного журнала, без query/token/session. Нельзя закреплять эти endpoint в пользовательской конфигурации: [официальное описание voice](https://github.com/discord/discord-api-docs/blob/main/developers/topics/voice-connections.mdx).

## Неуспешные прогоны сохранены

`.local/audit/discord-voice-sni-01` — обычный sniff не изменил результат. `-02` ещё не завершил полную проверку посредника. `-03` показал успех одного сервера, затем REP=4 при передаче имени другому серверу. `-04` — не завершился System DNS lookup под TUN. `-05` подтвердил все транспортные ожидания двух серверов, но не совпал один глобальный recovery-снимок. `-06` остановился при изменении адресов Teredo. `-07` выявил ложную блокировку Stop чужим тестовым sing-box; исправлено сохранением и проверкой `(EnginePid, EngineStartedUtcTicks)` в журнале. Старые журналы без identity остаются консервативными.

Транспорт, удаление собственных ресурсов и полное совпадение сети теперь представлены раздельно. Изменение Teredo/VPN не называется успешным полным восстановлением; исходный журнал сохраняется как unconfirmed. Проваленные отчёты не перезаписываются и не заменяются успешными статусами.

## Итог проверок и применение

`.local/audit/discord-voice-sni-08`: **12/12**, exit code 0, `AllSessionsFullBaselineMatched=true`. На обоих серверах исходный IPv4 и TCP/IPv4-совместимость с исходным IPv6 дали подтверждённый WebSocket Upgrade. Исходный IPv6, отказ SOCKS5 и отказ DoH дали ожидаемые ошибки. Отрицательные проверки содержат `ExpectedSuccess=false` и фактический `Probe.Success=false`, а не выдают отказ за успешное соединение. После всех двенадцати остановок подтверждены и собственная очистка, и полное совпадение baseline.

Автоматические проверки: Engine **164**, App **26**, Infrastructure **95**, Policy **133**, всего **418 passed** без failed/skipped. Дополнительно предыдущий полный Engine-прогон на минимальном sing-box 1.12.2: **163 passed**; добавленная затем проверка PID/startTime не меняет формат sing-box. Полный TUN-тест нового режима на 1.12.2 отдельно не выполнен. UI smoke: exit code 0, 12 снимков, форма профиля проверена визуально.

После подтверждения пользователя о закрытии старого PathFlux обновлены обычная Release-сборка и portable-папка. Создан отдельный профиль `OpenVpnProxy — Discord IPv4`; только активное Proxy-правило `Discord.exe` переведено на него. Исходный профиль сохранён, остальные правила не переводились на новый режим. Сохранена атомарная резервная копия `config.json.before-discord-ipv4-<UUID>`; профиль использует явный Docker NAT и показанный DoH endpoint. Факт авторизации в настоящем канале, двусторонний звук и Go Live остаются **Not Verified** до следующей пользовательской проверки.

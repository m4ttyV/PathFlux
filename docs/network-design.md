# Сетевая модель и проверка Windows

## Принятое решение

UI остаётся непривилегированным. Отдельный агент с UAC управляет проверенным sing-box и TUN `PathFlux-TUN`; конфигурация передаётся через ограниченный локальный named pipe. Системный proxy, `HTTP_PROXY` и `HTTPS_PROXY` не используются для прозрачного перехвата.

Минимальная версия sing-box — 1.12.2; EXE проверяется по сохранённому SHA-256, версии и платформе, затем через check. Совместимость описана в engine-compatibility.md. Живая документация sing-box содержит также поля более новых версий; добавлять их без проверки совместимости нельзя. Входящий TUN формируется с `auto_route: true`, `stack: mixed` для версий до 1.15 (начиная с 1.15 поле не задаётся), `strict_route: false`, MTU 1500, адресами `172.30.254.1/30` и `fdfe:7061:7468::1/126`. Автоматический выбор исходящего интерфейса задан через `route.auto_detect_interface`. В документации движка этот механизм указан для предотвращения route loops при auto_route; собственная приёмка Windows всё равно обязательна. [TUN и auto_route](https://sing-box.sagernet.org/configuration/inbound/tun/).

Порядок таблицы:

1. Direct для полных путей собственного `PathFlux.exe`, его `agent/PathFlux.Agent.exe` и выбранного `sing-box.exe`; одноимённые EXE из других каталогов не исключаются.
2. Внутренний DNS TUN: только `172.30.254.2` и `fdfe:7061:7468::2`, порт 53 TCP/UDP, inbound tun-in → hijack-dns.
3. Direct для IPv4/IPv6 loopback.
4. Если пользователь включил LAN bypass, Direct для `ip_is_private`.
5. Активные пользовательские правила: меньший `Priority` раньше; при равенстве UUID в ordinal-порядке канонической строки `D`.
6. Direct при отсутствии совпадений.

Имя EXE относится ко всем совпадающим именам. Полный путь относится ко всем экземплярам указанного EXE. Внешний движок документирует оба поля для Windows, но наличие полей не доказывает корректную атрибуцию в конкретном окружении. [Process name / path](https://sing-box.sagernet.org/configuration/route/rule/).

Для `Both` каждая исходная строка разворачивается на месте в UDP и TCP, сохраняя первый match. Block становится `reject`; Proxy TCP получает outbound профиля; Proxy UDP становится `reject` во всех профилях. SOCKS5 outbound дополнительно ограничен TCP. Ни успешный UDP ASSOCIATE, ни сохранённый результат UDP echo через relay не меняют эту политику: прозрачная UDP-маршрутизация по EXE через TUN ещё не прошла приёмку. Direct и Block можно назначать отдельно для TCP/UDP.

Если выбранный upstream недоступен, совпавший Proxy TCP не получает автоматический Direct outbound. Это поведение применимо внутри работающего движка. После аварии движка Direct-сеть может восстановиться, поэтому системный fail-closed / kill switch не заявлен. Правила Direct fallback отклоняются валидатором.

## DNS, LAN и IPv6

MVP использует системный local resolver, а не доказанную DNS-политику выбранного upstream. DNS приложения может обслуживаться отдельным процессом Windows и не соответствовать EXE-селектору. `strict_route` выключен; строгая защита DNS/IPv6 не заявлена. LAN bypass по умолчанию выключен и, если включён, имеет приоритет над пользовательскими правилами. Loopback всегда исключён. Это должно учитываться при тестах Block.

В исследованной исходной версии 1.12.12 движок [назначает DNS своего TUN на следующий адрес](https://github.com/SagerNet/sing-tun/blob/v0.7.3/tun_windows.go); генератор обслуживает эти виртуальные адреса через hijack-dns перед пользовательскими правилами. Это обязательное служебное исключение, в том числе для Block. Произвольные внешние DNS-адреса глобально не перехватываются. [Local resolver 1.12.12](https://github.com/SagerNet/sing-box/blob/v1.12.12/dns/transport/local/resolv_windows.go) исключает зарегистрированный собственный TUN из выбора системных DNS и использует DNS других подходящих активных адаптеров. Восстанавливается именно временный TUN с его DNS/адресами/маршрутами; исходные адаптеры PathFlux не перенастраивает. DNS после сети/VPN всё равно требует приёмки.

Адрес IPv6 в JSON подтверждает только сформированную настройку. Реальная IPv6 маршрутизация, утечки, ICMP и сетевые переходы требуют отдельного прогона. На этой стадии PathFlux нельзя считать изолирующим VPN или средством предотвращения утечек.

## Диагностика UDP relay без TUN

`IUdpRelayDiagnostics` проверяет upstream отдельными TCP/UDP-сокетами самого клиента. TCP-контроль, согласование SOCKS5, UDP relay и точная echo-цель проверяются независимо от таблицы TUN. Результат сохраняется с fingerprint параметров профиля, IP/портом цели, счётчиками и временем. Его актуальность ограничена 15 минутами и не превращается в runtime-capability движка.

Проверка не создаёт интерфейс, не меняет маршруты и не отправляет диагностический payload напрямую echo-серверу при отказе relay. UI требует остановить движок до UDP echo, поскольку результат сохраняется в профиле. Команды сервера и порядок проверки приведены в [udp-diagnostics.md](udp-diagnostics.md).

## Ручная приёмка selective TCP

Проводить на тестовой Windows 10/11 x64 с доступом к локальной консоли и контролируемым upstream. Перед запуском сохранить вывод `Get-NetRoute`, `Get-NetAdapter` и `Get-DnsClientServerAddress` вне репозитория. В `Settings` выбрать доверенный sing-box требуемой версии и SHA-256; проверить его официальный источник по инструкции разработки. Сетевые проверки не выполняются unit-тестами.

1. Зафиксировать прямой адрес выхода и соединения тестового EXE. Настроить два подконтрольных upstream с отличимыми логами или адресами выхода; `127.0.0.1:1080` является только примером, сервер должен существовать.
2. Создать профиль SOCKS5 и выполнить TCP-диагностику. Успех показывает возможность CONNECT через upstream, но ещё не прозрачный TUN.
3. Создать правило по имени тестового EXE, выбрать TCP, Proxy, Block-on-failure. Проверить конфигурацию и запустить. На UAC проверить запускаемый агент.
4. Создать новое TCP-соединение из тестового EXE без proxy-параметров приложения и переменных окружения. Подтвердить его на upstream или контролируемом сервере по отличимому адресу выхода. Проверить другой EXE без правила: ожидается Direct.
5. Для правила по пути запустить две копии тестового EXE с одинаковым именем в разных каталогах. Убедиться, что только выбранный путь использует upstream. Затем назначить разным EXE разные профили и проверить оба выхода.
6. Проверить Block, Direct, Enabled=false и перестановку приоритетов на новых соединениях. Существующие TCP-сессии не считать доказательством применения новой таблицы.
7. При Proxy Both проверить, что совпавший UDP отклоняется и не появляется на прямом канале. HTTP/HTTPS CONNECT не считать UDP-транспортом. Падение upstream не должно открывать Direct для совпавшего TCP внутри живого движка.
8. Остановить UI-командой, затем проверить восстановление маршрутов и прямой сети. Повторить с потерей IPC, завершением UI, аварией агента/движка, sleep/wake и изменением интерфейса в безопасном тестовом окружении.
9. Отдельно проверить TLS с корректным и некорректным сертификатом, неверные credentials, недоступный порт и отмену UAC. В JSON настроек, логах и файлах проекта не должно быть паролей.

Протокол прогона должен содержать версию Windows и движка, хеш бинарника, настройки VPN/Docker, правило/профиль без credentials, ожидаемый и фактический выход, время и результат восстановления. До появления такого протокола runtime-support остаётся `NotVerified`.

## Восстановление после сбоя

Сначала нажать «Остановить», дождаться остановки и проверить сеть. При недоступном UI закрыть его: агент контролирует родительский процесс/IPC и должен завершить движок. На этой стадии это механизм восстановления с неполной аварийной приёмкой, а не гарантия.

Если сеть не восстановилась, открыть PowerShell администратора локально, проверить PID и полный путь оставшегося `sing-box.exe` через Диспетчер задач и завершить только процесс PathFlux. Не завершать чужую VPN-сессию с таким же именем. Просмотреть оставшийся адаптер и его маршруты:

```powershell
Get-NetAdapter -Name 'PathFlux-TUN' -IncludeHidden
Get-NetRoute -InterfaceAlias 'PathFlux-TUN'
Get-NetRoute -DestinationPrefix '0.0.0.0/0'
Get-NetRoute -DestinationPrefix '::/0'
```

Отсутствие `PathFlux-TUN` после остановки нормально. Если движок уже завершён, а именно этот адаптер остался активен, проверить его принадлежность текущей сессии и отключить только его:

```powershell
Disable-NetAdapter -Name 'PathFlux-TUN' -IncludeHidden -Confirm
```

После отключения снова проверить прямую сеть и таблицу маршрутов. Не удалять все default routes и не выполнять глобальный сетевой reset. При сохранившемся нарушении сохранить вывод диагностики и перезагрузить тестовую Windows; сравнить маршруты/DNS с исходным снимком. Ручное восстановление произвольной сети вне собственного интерфейса пока не автоматизировано. [Get-NetRoute](https://learn.microsoft.com/en-us/powershell/module/nettcpip/get-netroute), [Disable-NetAdapter](https://learn.microsoft.com/en-us/powershell/module/netadapter/disable-netadapter?view=windowsserver2025-ps).

# ADR 002: точный PID отложен до проверенного источника атрибуции

Дата: 24.10.2026. Статус: принято для MVP; выбор технологии следующей вехи открыт.

## Решение

`ProcessInstance` и `IncludeChildren` присутствуют в модели расширения, но не реализуются через `process_name` / `process_path`. Активные правила точного PID, потомков и UntilProcessExit отклоняются компилятором с явной причиной. Источник атрибуции выделен контрактом `IConnectionAttributionProvider`; наличие списка процессов не считается таким источником.

## Основания

Документация Microsoft описывает ALE как WFP-слои для авторизации соединений и сокетных операций; application identity здесь задаётся нормализованным именем файла. Из этого нельзя вывести готовую семантику конкретного экземпляра процесса. [Application Layer Enforcement](https://learn.microsoft.com/en-us/windows/win32/fwp/application-layer-enforcement--ale-).

В таблице метаданных WFP PID присутствует на рядах ALE, включая AUTH_CONNECT и CONNECT_REDIRECT. Это подтверждает возможность исследования атрибуции, но не универсальную доступность PID на каждом пакете. [Metadata fields](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/metadata-fields-at-each-filtering-layer).

AUTH_CONNECT применяется к TCP connect и первому UDP-пакету для уникального remote tuple; CONNECT_REDIRECT меняет remote endpoint на время соединения. Поэтому TCP/UDP и жизненный цикл endpoint требуют отдельных экспериментов. [ALE layers](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-layers).

Для TCP-перенаправления через callout Microsoft предоставляет redirect handles и tracking, включая обнаружение повторного перенаправления. Эти механизмы важны при взаимодействии с другими прокси. Они не являются доказательством готового UDP-прокси. [Proxied connections tracking](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/using-proxied-connections-tracking).

## Исследовательский план

1. Создать изолированный Windows-прототип без изменений пользовательской модели. Сопоставлять событие сети с `(PID, startTimeUtc)` и сохранённым process handle, не с одним PID. Отдельно измерить задержку и гонки источников WFP/ETW/таблиц ОС.
2. Исследовать WFP callout и пользовательскую службу для TCP. Проверить исходный адрес назначения, redirect state, исключения агента и совместимость с другим прокси/VPN. Не выбирать драйвер до сравнения точности и сложности вариантов.
3. Отдельно исследовать UDP: endpoint lifetime, connected/unconnected sockets, новый remote tuple, мультикаст и shared sockets. Ошибка атрибуции должна давать диагностируемый Unsupported/Block в заявленном строгом режиме.
4. Для потомков вести граф по идентичностям экземпляров, а не именам EXE или PID. Проверить динамический старт, завершение родителя, reparenting/недоступность данных и повторное использование PID.
5. Проверить два экземпляра одного EXE с разными действиями, рестарт того же EXE, быстрый churn PID, два пользователя, повышенные и защищённые процессы, IPv4/IPv6 dual-stack. После завершения экземпляра UntilProcessExit не должен применяться к новому экземпляру с повторённым PID.
6. Если понадобится драйвер, отдельно определить WDK, процесс подписи и установки/удаления, ограниченный IPC, совместимость Windows 10/11 и сценарии аварии. Не отключать защитные механизмы ОС для обхода требований поставки.

Критерий допуска: воспроизводимые интеграционные тесты подтверждают точность TCP и UDP, отсутствие loops и корректное завершение. До этого UI и capability API продолжают возвращать Unsupported. Следующий ADR должен выбрать технологию по результатам экспериментов, а не по наличию имени PID в документации.

# Проверка маршрутизации Chrome, 25 октября 2026

Пользователь сообщил, что Chrome открывает сайты с обычным внешним IP при включённом PathFlux. В сохранённой конфигурации включены Proxy-правила `chrome.exe` по имени (TCP + UDP, приоритет 80) и по установленному пути (TCP, приоритет 100). Оба используют исходный SOCKS5-профиль; правило Discord использует отдельный профиль совместимости. Эти настройки не изменялись.

Контрольные HTTPS-запросы к `api.ipify.org` напрямую (`curl --noproxy '*' --ipv4`) и через `socks5h://127.0.0.1:1080` вернули один и тот же внешний IPv4. Проверка проводилась без работающего sing-box. Это наблюдение текущей сети: совпадение IP не доказывает обход SOCKS5 и не устанавливает причину общего выхода (например, совпадение VPN-серверов). Само по себе оно также не подтверждает маршрут обычной сессии Chrome.

## Интеграционный тест настоящего браузера

Добавлен режим NetworkLab:

```powershell
& $lab elevate browser-tcp $engine $sha $newAbsoluteOutput $absoluteChromeExe --allow-tun
```

Тест требует отсутствия другого sing-box и нового каталога отчёта. Он использует отдельные временные профили Chromium, headless automation, отключённый QUIC и явное сопоставление `example.com` с одним IPv4. Системный/браузерный прокси отключён только аргументом тестового экземпляра: путь к SOCKS5 должен обеспечить TUN. Правила компилируются обычным генератором PathFlux; TUN ограничен одним удалённым `/32`. Перед запросом проверяется сохранность остальных маршрутов и адаптеров.

Локальный SOCKS-наблюдатель разрешает только выбранные IPv4 и TCP-порт 443 и пересылает запрос реальному Docker SOCKS5 на `127.0.0.1:1080`. Успех требует загрузки страницы Example Domain, зарегистрированной пересылки через SOCKS5 и восстановления сети. Отрицательный сценарий возвращает SOCKS-отказ: страница не должна загрузиться, наблюдатель должен получить запросы, пересылок быть не должно. Исходные HTML и stderr браузера в отчёт не сохраняются.

Результат `.local/audit/chrome-tcp-03/report.json`: **3/3**, `PassedActualBrowserTcpSelectorsAndNoFallback`:

| Сценарий | Страница загружена | SOCKS-пересылки | SOCKS-отказы | Восстановление |
|---|---|---|---|---|
| process_path | Да | 1 | 0 | Подтверждено |
| process_name | Да | 1 | 0 | Подтверждено |
| Отказ upstream | Нет | 0 | 4 | Подтверждено |

Сборка NetworkLab: без ошибок и предупреждений. Предыдущие неуспешные отчёты `chrome-tcp-01` и `chrome-tcp-02` сохранены: первый не подтвердил загрузку/пересылку, второй отклонён на предварительной проверке браузера. В финальном тесте используется `--enable-automation`, поскольку Chromium иначе может повторно запуститься без повышения прав и отсоединиться от каналов вывода родителя; это поведение видно в [исходниках Chromium](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/chrome/app/chrome_main_delegate.cc).

## Границы результата

Тест подтвердил TCP-маршрутизацию реального автоматизированного Chrome с повышенными правами на sing-box 1.14.3. Он **не** подтверждает обычную пользовательскую сессию, ранее открытые соединения, QUIC/UDP, IPv6, DNS/ECH или конкретную установленную копию PathFlux. Поэтому сообщение пользователя не объявляется закрытой ошибкой, а рабочие настройки Discord и Chrome не заменяются предположительным исправлением.

Для следующей проверки обычной сессии нужны новые соединения Chrome после запуска движка и независимый признак прохождения через SOCKS5. Смена внешнего IP в этом окружении таким признаком не является. Отключать настоящий VPN или менять рабочие правила Discord ради различия IP не требуется.

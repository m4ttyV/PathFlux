# Этап 3: экспериментальный UDP в обычном PathFlux

Статус UDP: **Experimental**. Это интеграция в рабочее приложение и агент, а не заявление production-ready для Discord. Исходные [аудит TCP](network-audit-2026-10-24.md) и [UDP-аудит](udp-transport-audit-2026-10-24.md) остаются историческими отчётами. Системный kill switch — **Unsupported**.

Последующее исправление: [остановка при изменении стороннего VPN](vpn-transition-recovery.md). Удаление ресурсов PathFlux теперь проверяется отдельно от полного baseline; несовпавший исходный журнал сохраняется как unconfirmed. Результаты ниже описывают исходные прогоны этапа 3; отдельная повторная приёмка исправления приведена по ссылке.

## Включение

1. Остановить движок. В «Настройки → Экспериментальные функции» вручную включить «Разрешить экспериментальную UDP-маршрутизацию через SOCKS5» и сохранить настройки.
2. Открыть SOCKS5-профиль. Для обычного сервера выбрать **Standard SOCKS5**. Для контейнера с явной loopback-публикацией — **Docker NAT (Explicit Port Mapping)** и разрешённый диапазон UDP-портов. Сохранить профиль.
3. Для текущего стенда: TCP `127.0.0.1:1080`, UDP `20000–20030`. Эти значения не закреплены в приложении. Публикация должна сохранять номер порта: `host:p → container:p`. BND.PORT берётся из ответа каждой ассоциации; внутренний IP контейнера в Docker NAT не используется как адрес доставки.
4. В правиле выбрать TCP, UDP или TCP + UDP, нужный SOCKS5-профиль и имя/путь EXE. Для Discord предпочтительно постоянное правило по имени `Discord.exe`, если нужно охватить все экземпляры и меняющиеся каталоги версии. Точный PID и потомки не поддерживаются.
5. Запустить движок, подтвердить UAC только для агента. В «Диагностика → UDP — текущая сессия» проверить состояние и увеличение счётчиков при реальном UDP-трафике. Один успешный TLS-запрос не доказывает Proxy UDP.
6. После проверки остановить движок и убедиться, что остановка подтверждена. При ошибке восстановления сохранить recovery-журнал и исследовать причину, не выполняя глобальный reset.

Без opt-in совпавший Proxy UDP получает Reject. Включение не происходит после обновления и не зависит от исторического UDP echo. HTTP/HTTPS CONNECT не принимаются для активного UDP/Both Proxy-правила при включённом экспериментальном режиме: приложение показывает причину и предлагает TCP. Неактивные черновики правил не включаются в маршрутизацию.

## Архитектура и lifecycle

`AppSettings.ExperimentalSocksUdp` проходит через обычные хранилище, компилятор и IPC. Агент независимо проверяет конфигурацию, SHA-256/версию движка и создаёт `AgentUdpBridges`. На каждый используемый SOCKS5-профиль создаётся один `StrictSocksUdpBridge`, даже если правил несколько. Неиспользуемый профиль и TCP-only правило посредника не создают. DNS-имя TCP-прокси разрешается до изменения сети; это системный служебный DNS, без обещаний отсутствия утечек.

TCP outbound сохраняет исходные настройки профиля и `network=tcp`. Отдельный UDP outbound указывает на аутентифицированный IPv4 loopback-вход посредника. Случайные локальные credentials существуют только в памяти и конфигурации через stdin; профильные credentials остаются в DPAPI/защищённом IPC. Настройки, telemetry и recovery-журнал их не содержат.

Предварительная валидация UI использует инертные descriptors `127.0.0.1:9` только для `sing-box check`, который не устанавливает соединения. UI не создаёт слушателей или транспортных посредников. Настоящие endpoints подставляет агент перед запуском движка.

Агент отвечает успешным запуском только после готовности IP-интерфейса и наличия всех четырёх собственных /1 маршрутов на его интерфейсе. Ранее готовность интерфейса могла предшествовать установке маршрутов; UI acceptance поймал ответ при нулевых Proxy-счётчиках. Этот прогон сохранён как неуспешный.

Штатная остановка: sing-box завершается, закрывается Job Object, затем асинхронно освобождаются посредники и сравнивается исходный снимок сети. Собственные TCP/UDP-сокеты не принадлежат независимому фоновому сервису. Монитор падения sing-box освобождает посредники без ожидания следующего status-запроса и сохраняет Failed. При гибели агента Windows закрывает его sockets и Job Object завершает sing-box; recovery-журнал сохраняется для отдельной проверки.

Отказ одной upstream-ассоциации вызывает переподключение с новым сокетом/портом релея. Датаграммы во время разрыва теряются, не ставятся в очередь и не повторяются. Фатальная ошибка посредника закрывает его слушатель и активные ассоциации. Соответствующий sing-box UDP outbound остаётся направленным на недоступный аутентифицированный endpoint, без изменения маршрута на Direct; остальные профили и TCP не перенастраиваются. Для восстановления фатально остановленного посредника нужен Stop/Start.

За пределами живого TUN системного fail-closed нет. После исчезновения TUN новые соединения могут использовать обычные маршруты Windows. Это ограничение не устраняется успешным восстановлением сети.

## Хранилище и совместимость

Схема настроек — **2**. При чтении схемы 1 сохраняются UUID, профили, правила, credentialsRef и исторические результаты echo, но opt-in принудительно выключается, режим relay становится Standard без диапазона публикации. Исходный файл при чтении не перезаписывается; при первом сохранении используется существующий атомарный механизм с `.bak`. Будущие схемы не заменяются. Настройки Docker и режима relay входят в fingerprint нового UDP echo; старое несовместимое свидетельство не становится автоматически актуальным.

Standard использует буквальный BND.ADDR/BND.PORT; wildcard заменяется TCP peer. Доменное имя relay в transport guard пока не поддерживается. Docker NAT разрешён только для явно заданного `127.0.0.1`/`localhost`; удалённые прокси не распознаются как Docker автоматически. IPv6, удалённые SOCKS5 и другой NAT требуют своей приёмки.

## Диагностика

Через существующий status IPC передаются агрегаты по UUID профиля: состояние, активные ассоциации, 64-битные счётчики отправки/приёма, переподключения, FRAG, некорректные пакеты и фиксированная безопасная последняя ошибка. UI опрашивает раз в две секунды. Ни содержание пакетов, ни destinations приложения, ни username/password в статистику не включаются.

Кнопка сбора метрик записывает JSONL в `%LOCALAPPDATA%\PathFlux\diagnostics`, до 7200 снимков (обычно около четырёх часов). Кнопка также останавливает запись. Имя файла отображается рядом. Новый формат включает PID движка для разделения запусков.

```powershell
./scripts/summarize-udp-metrics.ps1 -Path 'C:\полный\путь\udp-....jsonl' -Output '.\udp-summary.json'
```

Счётчики sent/received асимметричны: их разница **не является потерями**. RTT/jitter/loss Discord из произвольных зашифрованных UDP-пакетов не вычисляются; summary явно пишет Not measured. UDP echo измеряет средний RTT только до подконтрольного echo endpoint; это не качество звонка. [Ручная приёмка Discord](discord-acceptance.md).

## Сетевые проверки

Все режимы, меняющие маршруты, требуют явных test-флагов. Выполнять последовательно. VPN, контейнер и сторонние WFP-фильтры не отключаются.

```powershell
./scripts/run-ui-udp-acceptance.ps1 -EnginePath $engine -EngineSha256 $sha -Output $newDirectory -RelayMode DockerNat -UdpPublishedPortFirst 20000 -UdpPublishedPortLast 20030 -Run
```

Этот режим запускает именно `PathFlux.exe`, использует команды обычного view model, JSON-хранилище, editor opt-in и настоящий UAC-агент. Изолированная конфигурация создаётся в новой папке отчёта; обычные пользовательские профили не заменяются. Проверяются TCP+UDP, TCP-only, UDP-only, Stop/Start, process_name, отказ неопубликованного порта и выключенный opt-in. Контрольный процесс должен сохранять Direct-доступ. Для Standard без Docker диапазона сценарий неопубликованного порта отсутствует.

Дополнительные явные режимы NetworkLab: `session-udp ... --allow-tun` проверяет реальный production EngineSession с контролируемыми независимыми SOCKS/echo-сокетами; `agent-faults ... <absolute-agent.exe> --allow-system-tun` — принудительное завершение собственных процессов production-агента/движка после подтверждения реального Docker UDP. Это отдельные сетевые тесты, не mock-подмена. Ошибки и промежуточные прогоны не перезаписываются.

## Результаты и ограничения

Реальный UI-прогон `.local/audit/stage3-ui-final`: **7/7**, TCP+UDP/UDP-only/Restart дали по одному ответу через посредник, process_name — два. При неопубликованном порте и выключенном opt-in selected UDP=0, control=1, TCP продолжил работать. Все семь восстановлений подтверждены. Создано 29 telemetry-снимков. Исходный `.local/audit/stage3-ui-01` отклонён из-за старого pending-журнала; `.local/audit/stage3-ui-02` обнаружил ответ без Proxy-счётчиков; `.local/audit/stage3-ui-03` подтвердил первые пять сценариев после исправления readiness. Они не выдаются за успешную финальную приёмку семи сценариев.

Старый recovery-журнал не совпал с текущей сетью после изменения адресов Windows OpenVPN и WSL. С явного разрешения пользователя его оригинальные байты сохранены в `.unconfirmed-...` с проверкой SHA-256, а новые тесты приняли текущую сеть за baseline. Историческое восстановление не объявлено подтверждённым; VPN/WFP не изменялись.

Первый lifecycle-прогон `.local/audit/stage3-session-01` прошёл семь сценариев, но остановился на pending-журнале: Teredo перешёл из detached в qualified между снимками. Независимый общий baseline уже совпал, однако собственный baseline отдельной сессии отличался. Это **неуспешный** прогон; его журнал сохранён отдельно как unconfirmed. Ожидание агента использует весь установленный 12-секундный recovery deadline вместо только трёх попыток. Стенд теперь требует также собственного Stopped-статуса сессии, а при позднем совпадении повторяет её проверку Stop.

Повторный `.local/audit/stage3-session-final`: **10/10** — Both, TcpOnly, UdpOnly, Restart, два профиля/приложения, отказ SOCKS5, reconnect control на прежнем клиентском UDP socket, FragmentedReply, BridgeCrash, EngineCrash. FRAG дал 0 ответов при 3 запросах к независимому echo и 3 отклонённых фрагментах. Reconnect дал 9/10 при двух ассоциациях. При аварии посредника UDP не достиг echo. Все десять восстановлений подтверждены и собственным агентским сравнением, и независимым снимком.

`.local/audit/stage3-agent-faults`: **2/2** с настоящими опубликованными агентом и IPC после подтверждения UDP через реальный Dante. При падении sing-box монитор освободил посредники и подтвердил recovery. При принудительном завершении агента Job Object завершил sing-box, журнал остался на месте и был архивирован как verified только после независимого точного сравнения baseline. Аварии не выдаются за системный kill switch.

Автоматические тесты: **383 passed, 0 failed, 0 skipped** — App 26, Engine 129, Infrastructure 95, Policy 133. Дополнительно Engine 129/129 на sing-box 1.12.2. Старые FRAG-тесты сохранены. Полная TUN-приёмка UDP на 1.12.2 в этом этапе отдельно не выполнялась.

TCP-регрессия `.local/audit/stage3-tcp-regression`: **3/3** с опубликованным production-агентом. Реальный Docker SOCKS5 пропустил TLS по process_path и process_name; отказ upstream не дал выбранному процессу Direct, контрольный процесс сохранил доступ. Во всех трёх случаях восстановление подтверждено.

Дополнительные прогоны опубликованной сборки сохранены без изменения результатов. `.local/audit/stage3-ui-published` завершился неуспешно на UnpublishedPort: UDP корректно заблокирован, но внешний TLS-probe не прошёл; причина этого единичного TCP-отказа не установлена. В `.local/audit/stage3-ui-published-02` все транспортные проверки прошли, включая TLS, однако немедленный снимок после последнего Stop отличался от общего baseline. Последующий снимок в finally уже совпал, pending-журнала и живых процессов не осталось. Прогон остался **Failed**. Для следующей проверки стенд сохраняет первоначальные причины и все повторные снимки, ждёт точного совпадения до 12 секунд и дополнительно требует Stopped от агента; критерии сравнения не ослаблены. Это не подтверждает причину временного расхождения.

`.local/audit/stage3-ui-published-03`: **Failed** на ProcessName — STUN через посредник и контрольный STUN прошли, TLS завершился OperationCanceledException. Все пять выполненных остановок получили Stopped и точное совпадение baseline. Для расследования TLS-probe теперь указывает стадию Connect/Handshake/HttpWrite/HttpRead в безопасном коде ошибки, без endpoint и текста исключения; прежний общий deadline 8 секунд сохранён. Независимые пять TLS-запросов к example.com напрямую через Docker SOCKS5 без PathFlux/TUN прошли за 0,51–0,60 секунды (`stage3-direct-socks-tls.json`). Это сравнение не устанавливает причину предыдущего тайм-аута и не заменяет неуспешный прогон успешным. Стабильная повторяемость TCP во всех длительных совмещённых сценариях пока **Not Verified**.

Финальная опубликованная сборка, `.local/audit/stage3-ui-published-04`: **7/7 Passed**, exit code 0. TCP+UDP, TCP-only, UDP-only, Restart, ProcessName, UnpublishedPort и OptInDisabled прошли с прежними условиями. Во всех семи случаях первичный снимок восстановления уже совпал с baseline, повторное ожидание не понадобилось; агент вернул Stopped. JSONL содержит 37 снимков; summary корректно разделил запуски и получил 5 отправленных / 5 полученных proxy-пакетов. Это транспортные счётчики, не оценка потерь или качества Discord. После завершения отдельно подтверждены отсутствие живых Agent/sing-box, PathFlux-TUN и активного recovery-журнала; оба unconfirmed-архива сохранены. Успех этого прогона не устанавливает причину предыдущих TLS-тайм-аутов.

Финальный UI smoke завершился с кодом 0, созданы 12 снимков двух тем; настройки opt-in и диагностика проверены визуально. `git diff --check` прошёл. Документы, примеры и диагностические скрипты включены в `artifacts/win-x64` вместе с опубликованными UI, агентом и NetworkLab; требуется установленный .NET 10 Runtime x64, sing-box отдельно.

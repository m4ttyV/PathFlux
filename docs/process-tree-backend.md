# Точное дерево процессов: экспериментальный TCP backend

Статус: **Experimental**, выключено по умолчанию. Реализовано дерево конкретного экземпляра процесса, включая новых детей и внуков. Подстановка дочерних EXE в глобальные правила по имени/пути не используется. UDP-правила дерева **не приняты** и запрещены при запуске через UI/агент. TCP-правило не выбирает UDP: он подчиняется остальным правилам и маршруту по умолчанию Direct. Рабочая пользовательская конфигурация и установленный официальный движок автоматически не заменяются.

## Идентичность и область правила

Корень задаётся `ProcessInstanceId(Pid, StartTimeUtc, SequenceNumber)`. PID, время создания Windows FILETIME и системный номер экземпляра проверяются вместе. Время и sequence передаются в JSON движка десятичными **строками**, чтобы обработка чисел через float64 не потеряла младшие разряды. Только PID без идентичности не принимается.

`IncludeChildren=true` разрешён только для корня `ProcessInstance`. По имени или пути нельзя незаметно получить приблизительное дерево. Без IncludeChildren тот же селектор охватывает только корневой экземпляр. После перезапуска корневого приложения нужно выбрать его новый PID; старое правило не переносится на новый экземпляр или другой процесс с повторно использованным PID.

Список процессов получает время, sequence и доступный parent PID через handle с `PROCESS_QUERY_LIMITED_INFORMATION`. Сетевой backend читает родство независимо через `NtQueryInformationProcess`: BasicInformation и ProcessSequenceNumber (класс 92). Порядок предков и исключение заведомо более старых процессов определяются системной последовательностью, а не UTC: изменение часов не должно отправлять потомка на Direct. Эти native API требуют отдельной проверки на каждой поддерживаемой версии Windows; отсутствие данных означает отказ.

На каждом новом TCP-соединении backend определяет владельца Windows endpoint и проверяет его живую идентичность. Затем проходит цепочку родителей. Новому ребёнку не нужно ждать опроса UI. PID предка, время и sequence защищают от наследования связи после повторного использования PID. Посторонний экземпляр того же EXE не получает правило дерева.

Кеш принадлежит процессу движка и индексируется полной идентичностью. Уже доказанные связи сохраняются после выхода родителя. Максимум — 4096 записей и 128 звеньев при обходе; очистка кеша может привести к блокировке осиротевшего процесса, если его родство больше нельзя восстановить. Ненаблюдавшийся потомок, чей родитель уже завершился, остаётся Unknown. Неполная цепочка не считается подтверждением отсутствия принадлежности.

## Маршрутизация и fail-closed

Порядок существующих правил сохраняется. Для дерева генерируются два условия подряд: подтверждённая принадлежность с выбранным действием и Unknown с Reject. Обе проверки используют одно решение на поток: повторное чтение между положительным условием и Unknown-guard не может превратить Unknown в Inside и пропустить поток на Direct. Подтверждённо посторонний процесс проходит к следующему правилу. Более приоритетные явные правила и внутренние исключения PathFlux сохраняют своё значение. Прокси не получает Direct fallback.

Windows TUN может изменить удалённый TCP endpoint, видимый IP Helper. Поэтому для исходного локального endpoint собираются все возможные владельцы; неоднозначность отклоняется вместо выбора первой строки. Поиск владельца и живая идентичность перепроверяются. Обычный кеш маршрутизатора по сетевому tuple для режима дерева отключён.

Это всё ещё пользовательские снимки IP Helper, **не атомарный WFP flow token**. Стресс-приёмка гонок между поиском владельца, закрытием сокета и повторным использованием endpoint не завершена. Абсолютная гарантия атрибуции каждого пакета и production-ready статус не заявляются. Неподтверждённые данные блокируются, однако отсутствие всех возможных гонок снимков пока не доказано.

System DNS, существующие VPN/WFP и отсутствие системного kill switch сохраняют прежние ограничения. Уже открытые соединения не засчитываются за проверку нового правила. Проверяются новые соединения при живом корне; перезапуск корня требует нового правила PID.

## Отдельный движок

Официальный sing-box 1.14.3 содержит `process_name` и `process_path`, но не условие точного дерева: [исходники правил](https://github.com/SagerNet/sing-box/blob/v1.14.3/option/rule.go). Поэтому добавлен отдельный overlay исходников в `backends/process-tree`, а не фиктивная галочка для обычного бинарника.

Сборка закреплена на upstream **v1.14.3** и **Go 1.25.5 windows/amd64**, `CGO_ENABLED=0`, `with_gvisor`, `trimpath`, без случайной VCS-ревизии внешнего репозитория. Это **модифицированная, не официальная сборка sing-box**. SHA-256 исходного ZIP проверяется перед распаковкой. Каталог результата содержит изменённые исходники, лицензию upstream и manifest фактического бинарника. Go-модули проверяются через upstream go.sum.

UI сначала проверяет SHA-256 и версию, затем отдельную команду `pathflux-capabilities`, protocol 3: дерево, время создания, sequence, единое решение на поток и наличие прототипа UDP owner guard. Агент повторяет эти проверки независимо. Возможности — описание протокола, а не сертификат production-приёмки. Обычный официальный бинарник с включённым режимом дерева отклоняется до TUN. При выключенном режиме поддержка официальных версий от 1.12.2 сохраняется.

Для сборки из проверенного архива:

```powershell
# $archive: ZIP https://codeload.github.com/SagerNet/sing-box/zip/refs/tags/v1.14.3
# $go: полный путь к go.exe версии 1.25.5 windows/amd64
# $newOutput: новый абсолютный каталог
./backends/process-tree/build.ps1 -SourceArchive $archive -Go $go -OutputDirectory $newOutput
```

Ожидаемый SHA-256 source ZIP: `5BF11EEB2F5B93377166AF1ECDCF24DD2C4BE3C92BCB43C09D95EDD01EB85949`.
Использованный официальный Go ZIP: `go1.25.5.windows-amd64.zip`, SHA-256 `ae756cce1cb80c819b4fe01b0353807178f532211b47f72d7fa77949de054ebb`. Каталог Go может оставаться локальным: системная установка не требуется.

## UI

1. При остановленном движке указать отдельную сборку backend и её SHA-256. В настройках явно включить и сохранить «Точное дерево PID — отдельный backend (Experimental)».
2. В списке процессов выбрать живой корень с доступной идентичностью и нажать «Дерево выбранного PID».
3. Проверить созданное TCP-правило, профиль и приоритет. `IncludeChildren` можно снять для правила только корневого экземпляра. Если нужна изоляция одного дерева, перекрывающие глобальные EXE-правила нужно отключить явно: они продолжают действовать независимо.
4. Выполнить валидацию и запустить. Старт проверяет, что корневой экземпляр ещё существует.

Нельзя включить UDP дерева: `ValidateEngineActivation` отклоняет TCP+UDP/UDP для ProcessInstance/IncludeChildren и в UI-адаптере, и в агенте до запуска сети. Обычные UDP-правила по EXE этой проверкой не заменяются. В режиме только TCP дерева экспериментальный UDP owner guard не подключается к обычным UDP-ассоциациям.

## Тесты и неподтверждённые возможности

NetworkLab поддерживает:

```powershell
& $lab elevate process-tree $engine $sha $newReport --allow-tun
& $lab process-tree-agent $engine $sha $newReport $agent --allow-system-tun
# Отдельный лабораторный UDP-прототип; не разрешает UDP в пользовательских правилах:
& $lab elevate process-tree-udp $engine $sha $newReport --allow-tun
```

TCP-сценарии запускают свежих детей и внуков уже после TUN. Один и тот же child EXE запускается также вне дерева как Direct-контроль. Посредник считает фактические SOCKS5 CONNECT к Docker; TLS проверяется до настоящего сервера. Отказ SOCKS5 должен прервать выбранное соединение при доступном Direct-контроле. После каждого сценария проверяется сеть. Изолированный `/32` и настоящий UAC/IPC-агент со стандартными маршрутами представлены отдельными режимами.

Автоматические проверки: **425 .NET** (170 Engine, 27 App, 95 Infrastructure, 133 Policy) на официальном sing-box 1.14.3 и **13 Go** (12 ядра и один маршрутизатора). Go-проверки включают новые потомки, посторонний тот же EXE, PID reuse, повторный PID с тем же UTC временем и другим sequence, откат UTC, сохранение доказанного осиротевшего дерева, недоступный родитель, SelfOnly, предел глубины кеша и стабильность решения Unknown между правилами. Запрет активации UDP дерева проверяется отдельно в .NET.

Итог опубликованной сборки: `.local/audit/process-tree-agent-release-03/report.json`, **3/3**, `PassedProductionAgentProcessTreeTcp_UdpNotAccepted`, `CallerElevated=false`. Использованы опубликованные агент и NetworkLab, стандартный TUN, непривилегированные корень/потомки и настоящий Docker SOCKS5/OpenVPN. Новые ребёнок и внук загрузили HTTPS через наблюдаемый SOCKS5; такой же EXE вне дерева прошёл Direct-контроль. При SOCKS-отказе фактический `Selected.Success=false`, `ExpectedSelectedSuccess=false`, зарегистрирован один отказ без пересылки; Direct-контроль остаётся доступным. После каждой из трёх остановок подтверждено полное совпадение baseline. Это ограниченная TCP-приёмка, не приёмка UDP дерева или всех гонок.

UI smoke опубликованного приложения: exit code 0, **12 снимков** двух тем; формы настроек и правил проверены визуально. Portable UI/агент: `artifacts/win-x64`. Отдельный движок со всеми изменёнными исходниками, overlay и лицензией: `artifacts/process-tree-experimental`. SHA-256 итогового `sing-box.exe`: `3149B341FC2AC1F8E383C6A54C5DD3E4BF2E0DEE8901C8A435903A08C0594C81`; фактические возможности protocol 3 сохранены в `build-manifest.json`. Установленная пользовательская копия и настройки не обновлялись автоматически.

Предыдущие неуспешные отчёты `.local/audit/process-tree-01`–`05` сохранены. Выявлены вывод capabilities в stderr, несовпадение удалённого TCP endpoint после TUN и потеря точности большого численного FILETIME. В `-05` три TCP-сценария прошли, UDP не дал ответа/ассоциации. Там же полный recovery не совпал из-за изменения адресов/маршрутов адаптера Teredo; отчёт **RecoveryNotConfirmed** не заменён успешным статусом. В сохранённом снимке оба PathFlux-интерфейса detached. UDP-провал не является успешной UDP-приёмкой.

UDP дерева, повторное использование UDP-порта другим процессом, атомарность атрибуции при гонках endpoint, осиротевшие процессы до первого наблюдения, длительная нагрузка и совместимость всех Windows остаются **Not Verified**. Перед production необходимы отдельный аудит и расширенная сетевая приёмка. Рабочий режим Discord/Chrome на официальном движке этим прототипом автоматически не заменяется.

Native API проверены по [Microsoft NtQueryInformationProcess](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntqueryinformationprocess) и [исходным определениям System Informer](https://github.com/winsiderss/phnt/blob/master/ntpsapi.h). Внутренние API могут изменяться; они не дают оснований объявлять поддержку непроверенных Windows.

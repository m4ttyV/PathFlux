# Проверка SOCKS5 UDP relay

Диагностика второй итерации проверяет реальную передачу случайных echo-пакетов через выбранный SOCKS5 upstream. Для неё не нужен TUN или UAC. Проверка создаёт собственные TCP/UDP-сокеты; она не перехватывает пакеты Discord или другого EXE.

Успешное согласование UDP ASSOCIATE означает только выделенную сервером ассоциацию. Для `Verified` новая проверка должна получить через relay все 3–8 точных ответов с непредсказуемыми payload. Каждый payload содержит 64 случайных байта; дубликаты, старые nonce, чужой relay, неверный внутренний IP/порт и некорректные пакеты не засчитываются. Потеря TCP-контроля или timeout дают неуспешный результат. При отказе relay диагностические данные не пересылаются напрямую цели.

`Verified` относится к этому IP/порту и моменту теста. Он не подтверждает прозрачную UDP-маршрутизацию через TUN, голос Discord, QUIC, длительную устойчивость, другие IP-семейства или размеры датаграмм. Генератор продолжает отклонять совпавший Proxy UDP даже при актуальном свидетельстве. `Direct fallback` не включается.

## Контролируемый echo endpoint

Нужны Python 3 и IP-адрес сервера, доступный **со стороны SOCKS5 upstream**. Скрипт возвращает payload без изменений, принимает не более 1024 байт, не пишет содержимое пакетов в журнал и не меняет firewall. По умолчанию он слушает только loopback.

Для локального лабораторного SOCKS5, который может обращаться к loopback этой же Windows:

```powershell
python scripts/udp-echo-server.py --bind 127.0.0.1 --port 4444 --count 3
```

На отдельном подконтрольном сервере скопировать скрипт и привязать его к доступному серверному адресу. Например, все IPv4-интерфейсы:

```text
python udp-echo-server.py --bind 0.0.0.0 --port 4444 --count 0
```

В диагностике указать реальный IP этого сервера, не `0.0.0.0`. Доступ к UDP/4444 должен разрешаться принятой политикой лаборатории; PathFlux не создаёт правил firewall. `--count 0` работает до Ctrl+C; `--count 3` завершает сервер после трёх ответов.

IPv6 проверять отдельно: привязать сервер к его конкретному unicast IPv6-адресу и указать этот адрес в UI. Серверный IPv6-сокет работает отдельно от IPv4. Scoped и link-local IPv6 в диагностике не поддерживаются.

Если SOCKS5 находится в Docker, `127.0.0.1` в адресе echo-цели относится к его сетевому пространству. Если SOCKS5 удалённый, это loopback удалённого сервера. Для echo на Windows-хосте нужен адрес, достижимый именно из контейнера/удалённого upstream.

## Порядок проверки

1. Остановить сетевой движок PathFlux, чтобы проверить relay независимо от TUN.
2. Сохранить SOCKS5-профиль с корректным endpoint и авторизацией, если она требуется. Запустить подконтрольный echo-сервер.
3. В диагностике выбрать профиль, literal IP echo-цели и порт. DNS-имена, wildcard, multicast, broadcast, scoped/link-local IPv6 не принимаются. Нормальный IPv4-mapped IPv6 приводится к IPv4.
4. Выполнить UDP echo. Проверить стадию, число отправленных/полученных пакетов и результат. `Verified` ожидается только при всех точных ответах; недоступный сервер, потери или неверный ответ означают Failed. Неподдерживаемая команда ASSOCIATE означает Unsupported.
5. Закрыть echo-сервер и повторить: успех повторяться не должен. Повторить с закрытым proxy-портом, неверной авторизацией и TCP-only upstream.
6. Убедиться, что результат сохранился после перезапуска клиента. Изменить endpoint или авторизацию профиля: старое свидетельство должно стать неактуальным. Повторить тест после изменения.

Среднее время ответа является диагностическим измерением короткого теста. Оно не является гарантией будущей задержки. Все ответы относятся к одной ассоциации и одному UDP-сокету.

## Сохранение и актуальность

Необязательное поле `UdpVerification` добавлено в профиль без изменения `schemaVersion: 1`; старый профиль без этого поля читается как непроверенный. Хранятся fingerprint, время UTC, результат, literal IP/порт, счётчики и среднее время ответа. Пароль, echo payload и nonce в свидетельство не записываются.

Fingerprint зависит от UUID, протокола, host/port, credentialsRef и TLS server name. Имя и Enabled не меняют идентичность upstream; замена credentials создаёт новую opaque-ссылку и требует нового теста. Срок актуальности — 15 минут включительно, будущее время не принимается. Для `Verified` нужны 3–8 отправленных пакетов, столько же ответов, допустимый endpoint и корректная метрика, если она сохранена. Это локальная история теста, не право включить UDP TUN.

## Протокольные ограничения

Клиент привязывает UDP-сокет до ASSOCIATE и сообщает его endpoint. TCP-контроль остаётся открытым; его завершение отменяет ассоциацию. Ответы отправляются relay endpoint из BND.ADDR/BND.PORT. Фрагментация не реализуется, поэтому FRAG ≠ 0 отбрасывается. Основание: [RFC 1928, разделы 6–7](https://www.rfc-editor.org/rfc/rfc1928).

Для совместимости wildcard BND.ADDR заменяется IP управляющего TCP-соединения с сохранением BND.PORT. Это локальное правило совместимости диагностики, а не отдельная гарантия RFC. Relay должен иметь совместимое IP-семейство и ненулевой порт. DNS-имя relay, возвращённое самим upstream, разрешается с ограниченным временем ожидания; echo-цель остаётся literal IP. GSSAPI и иные способы method-specific encapsulation не поддерживаются; доступны no-auth и username/password.

## Автоматические проверки

```powershell
dotnet test tests/PathFlux.Policy.Tests/PathFlux.Policy.Tests.csproj -c Release
dotnet test tests/PathFlux.Infrastructure.Tests/PathFlux.Infrastructure.Tests.csproj -c Release
```

Тесты используют локальные контролируемые сокеты и проверяют positive/negative relay-сценарии, метаданные, старение и отсутствие автоматического разрешения TUN UDP. Они не заменяют внешний upstream-прогон и ручной Windows selective-routing acceptance из [network-design.md](network-design.md).

## Лабораторный прогон официального движка

Дополнительные `UdpDataplaneTests` запускают выбранный официальный sing-box от 1.12.2 без повышения прав и системных маршрутов:

```powershell
$installed = ./scripts/get-engine.ps1
$env:PATHFLUX_TEST_ENGINE = $installed.EnginePath
$env:PATHFLUX_TEST_ENGINE_SHA256 = $installed.EngineSha256
dotnet test tests/PathFlux.Engine.Tests/PathFlux.Engine.Tests.csproj -c Release --filter 'FullyQualifiedName~UdpDataplaneTests'
```

Без `PATHFLUX_TEST_ENGINE` эти тесты пропускаются. Перед запуском проверяются PATHFLUX_TEST_ENGINE_SHA256 и версия; бинарник удерживается открытым на время процесса. Конфигурация существует только внутри теста: TUN заменён локальным SOCKS-входом, правила процессов заменены маршрутом к лабораторному upstream, ограничение SOCKS outbound `network: tcp` удалено. Рабочая конфигурация приложения этих изменений не получает.

Положительный сценарий проверяет цепочку «диагностический клиент → официальный sing-box → SOCKS5 upstream с авторизацией → независимый UDP echo». Счётчики upstream и отдельного echo-сокета подтверждают реальную передачу трёх различных payload. Отрицательный сценарий возвращает от upstream `REP=7`; напрямую доступный echo-сокет должен получить ноль пакетов, а диагностика завершиться неуспешно.

Этот прогон подтверждает UDP-транспорт backend в изменённой лабораторной конфигурации. Он не проверяет TUN, EXE/name/PID-атрибуцию, системный DNS, внешнюю сеть или UDP произвольного приложения. Production-генератор по-прежнему ограничивает SOCKS TCP и отклоняет Proxy UDP независимо от результата лаборатории.

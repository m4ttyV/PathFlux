# Проверка TCP/UDP через Windows TUN

NetworkLab использует компилятор правил PathFlux, проверяет версию и SHA-256 выбранного движка и сохраняет исходную сеть до любых изменений. Полные отчёты содержат локальную сетевую топологию и остаются в игнорируемом каталоге; перед публикацией требуется просмотр.

## Подготовка без изменения сети

```powershell
$engine = .\scripts\get-engine.ps1 -Version 1.14.3
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256
```

Подготовка проверяет клонированный EXE и девять конфигураций через check. Она не создаёт TUN. `Prepared_NoTunStarted` не означает успешной сетевой приёмки.

## Изолированные прогоны

```powershell
# Только лабораторная цель 198.18.0.1/32 и собственная подсеть интерфейса.
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256 -Run -Elevate

# Один IPv4-адрес example.com:443 через наблюдаемый SOCKS-шлюз и Docker 127.0.0.1:1080.
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256 -Suite DockerTcp -Run -Elevate

# Экспериментальный UDP, не меняет пользовательские настройки и правила.
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256 -Suite ExperimentalUdp -Run -Elevate
```

`-Elevate` явно вызывает UAC. Без этого флага нужен уже повышенный PowerShell. Нужен новый каталог каждого прогона; его задаёт `-Output`, иначе используется `lab-results/<UUID>`. Скрипт предпочитает portable-бинарник; сначала опубликовать актуальную сборку через publish.ps1.

Для версий до 1.14 стенд использует gVisor и адрес /32. Начиная с 1.14 — адрес /30, mixed (до 1.15) и явный dns_mode=disabled. Системный TCP stack требует дополнительный адрес, поэтому mixed с /32 не работает. В sing-box 1.14.3 автоматическое определение TUN DNS при /32 без IPv6 приводило к panic, хотя check проходил. Начиная с 1.15 поле stack не задаётся. Производственный режим использует собственную обычную конфигурацию, а не эту подмену.

Активный VPN с маршрутами 0.0.0.0/1 и 128.0.0.0/1 допускается в узком стенде: эти маршруты сохраняются, перехватывается только цель /32. Более специфичный конфликт лабораторной цели или адресов 172.30.254.0/30 запрещает запуск. Активные интерфейсы PathFlux тоже запрещают запуск. Полностью отсоединённые фантомные записи Down/NotPresent без IP-протоколов, адресов и DNS игнорируются.

## Проверка настоящего агента и системных маршрутов

В корне опубликованной portable-папки:

```powershell
$lab = (Resolve-Path '.\network-lab\PathFlux.NetworkLab.exe').Path
$agent = (Resolve-Path '.\agent\PathFlux.Agent.exe').Path
$output = Join-Path $PWD ('lab-results\agent-' + [guid]::NewGuid().ToString('N'))
& $lab agent-tcp $engine.EnginePath $engine.EngineSha256 $output $agent --allow-system-tun
```

Этот режим **временно меняет системные TUN-маршруты**, запускает настоящий агент через UAC и использует обычный production-генератор. Выполняются process_path, process_name и отказ upstream при доступном Direct. Подтверждаются TLS-ответ и число соединений, прошедших наблюдаемый шлюз к реальному Docker SOCKS5. Сам Docker не перенастраивается. Агент сравнивает свой baseline, а контроллер независимо сравнивает исходную сеть после каждой сессии.

## Что доказывают сценарии

Две копии PathFlux.LabProbe.exe имеют одинаковое имя и разные полные пути. TCP echo-сценарии проверяют случайный 64-байтовый запрос и подтверждённый echo независимого сервера через нужный шлюз. Девять сценариев: Path, Name, Disabled, Block, Priority, ProfileTwo, UpstreamRefused, EngineCrash, JobClose. Последние два проверяют восстановление после аварии движка и закрытия его Job Object; принудительное закрытие job не выдаётся за отдельный тест падения UI или агента.

Docker-сценарии проверяют TLS example.com с обычной проверкой сертификата. Контрольный процесс сохраняет доступ к Direct. Поэтому отказ выбранного Proxy при работающем контроле подтверждает отсутствие Direct fallback; одна лишь недоступность синтетической цели такой проверки не заменяет.

Проверяются все строки маршрутов (включая VPN split-default), DNS и адреса исходных адаптеров, а также отсутствие подключённого собственного IP-интерфейса. При расхождении или неизвестном результате возвращается ненулевой код и сохраняется отчёт. Нет глобального reset сети, удаления чужих маршрутов или отключения VPN.

## UDP остаётся закрытым в приложении

UDP-режим доступен только в NetworkLab через внутреннюю лабораторную ветку генератора и строгий UDP-посредник. UI, настройки schema1 и IPC агента её не включают. Порядок правил и Block сохраняются, HTTP/HTTPS UDP остаётся Reject. Производственный SOCKS outbound сохраняет network=tcp; отдельный UDP outbound создаётся только для зарегистрированного посредника.

В исходном аудите **FragmentedReply не прошёл**: штатный parser sing-box 1.14.3 доставил ответы с FRAG=1. В обновлённом стенде проверка сохранена, но посредник обязательно отклоняет все ненулевые FRAG. Добавлены отрицательные заголовки, потери, reconnect на том же socket, аварийная остановка и минутная нагрузка. Неудачные исторические отчёты сохраняются. Текущие результаты и ограничения: [аудит UDP](udp-transport-audit-2026-10-24.md).

Для реального Docker/Dante/OpenVPN используется `-Suite DockerUdp -UdpPublishedPortFirst 20000 -UdpPublishedPortLast 20030`: STUN UDP/3478, правила path/name, отказ порта вне публикации, production Reject, engine crash и job close. Адрес контейнера не закрепляется; возвращённый динамический порт должен входить в явно заданный диапазон. Публикация должна сохранять номер порта. Диапазон не применяется автоматически ко всем SOCKS-профилям.

Прямой DNS/53 под TUN в текущем окружении блокируется существующими WFP-фильтрами OpenVPN, что отдельно зафиксировано как неуспешная проверка. Для проверки реального DNS relay без TUN доступен `PathFlux.NetworkLab docker-udp-relay <новая абсолютная папка>`. Его положительный результат не является приёмкой DNS через TUN или Discord.

## Неподтверждённое восстановление

Журнал агента хранит baseline. Пока он остаётся неподтверждённым, приложение не объявляет остановку успешной и не запускает новую сессию. Для проверки и архивирования без изменения сети:

```powershell
$journal = Join-Path $env:LOCALAPPDATA 'PathFlux\network-recovery.json'
& $lab recover-journal $journal --archive-confirmed
```

Команда требует отсутствия живого агента и точного совпадения текущих маршрутов, DNS и адресов с baseline. Только после успеха файл переименовывается в .verified-<UUID>; сеть не правится. При несовпадении исходный файл сохраняется. Старые журналы без baseline не позволяют выполнить эту проверку.

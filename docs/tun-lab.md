# Изолированная проверка TCP через TUN

`PathFlux.NetworkLab` — отдельный стенд для проверки правил по пути и имени процесса на Windows. Он использует компилятор правил приложения, официальный закреплённый sing-box и общий с агентом Windows Job Object. Настройки пользователя и DPAPI-хранилище не используются.

## Подготовка без изменения сети

После Release-сборки или из portable-папки:

```powershell
$engine = .\scripts\get-engine.ps1 -Version 1.12.2
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256
```

По умолчанию TUN не запускается. Стенд проверяет SHA-256 движка, читает маршруты и параметры адаптеров, создаёт две копии тестового EXE в разных каталогах, проверяет одну через независимый loopback TCP echo-сервер и выполняет `sing-box check` для шести конфигураций. Каталог `lab-results/<UUID>` создаётся заново при каждом запуске; путь можно задать через `-Output`. Подготовка может пройти при конфликтующих маршрутах: поле `PreflightAllowsTun=false` означает, что сетевой запуск запрещён.

## Сетевой прогон

В PowerShell с правами администратора:

```powershell
.\scripts\run-tun-lab.ps1 -EnginePath $engine.EnginePath -EngineSha256 $engine.EngineSha256 -Run
```

Скрипт не повышает права автоматически. Явный `-Run` разрешает временный интерфейс `PathFlux-Lab-TUN` с адресом `172.30.254.1/32` и только маршрут `198.18.0.1/32`. Первое использование sing-box может установить драйвер Wintun. Конфигурация стенда не задаёт IPv6 и маршруты по умолчанию. Префикс `/32` выбран без следующего адреса для автоматического TUN DNS; фактическое восстановление проверяется снимками системы.

Перед запуском требуется отсутствие интерфейсов PathFlux и любых маршрутов, кроме default, покрывающих лабораторную цель или адрес интерфейса. Включая VPN split-default `/1`: стенд откажется от такого прогона. Он не отключает VPN и не удаляет чужие маршруты. Использовать подходящую тестовую Windows-машину без конфликта.

## Сценарии и доказательства

Обе копии называются `PathFlux.LabProbe.exe`, но имеют разные полные пути. Они используют TCP-сокеты к числовому IP, без системного прокси. Два локальных SOCKS5-шлюза принимают только лабораторную цель и пересылают данные независимому TCP echo-серверу. Для каждой попытки используется случайный 64-байтовый запрос; шлюз учитывает SHA-256 только после подтверждённого echo. Успешный ответ и ожидаемый шлюз проверяются вместе.

| Сценарий | Ожидаемый результат |
|---|---|
| Path | Только выбранный полный путь проходит через первый шлюз |
| Name | Обе копии с одинаковым именем проходят через первый шлюз |
| Disabled | Выключенное правило не отправляет запросы шлюзам |
| Block | Блокируемый процесс не получает echo и не достигает шлюзов |
| Priority | Более ранний Block перекрывает Proxy |
| ProfileTwo | Выбранный путь проходит только через второй шлюз |

После каждого сценария движок завершается. Проверяются исходные default routes, DNS и адреса существовавших адаптеров, исчезновение лабораторного интерфейса и отсутствие добавленного маршрута к цели. Если очистка не подтверждена, результат `RecoveryNotConfirmed` и ненулевой код завершения. Глобального reset сети нет. При аварии контроллера Job Object завершает привязанный движок; это не заменяет проверку восстановления сети после аварии на реальном TUN.

`report.json` сохраняется до возможного создания TUN и после проверок. Он содержит локальные сетевые адреса, маршруты и имена адаптеров; перед публикацией требуется просмотр. Паролей, содержимого пакетов и исходного stderr движка в нём нет. `Prepared_NoTunStarted` подтверждает только подготовку; `PassedIsolatedTcpTunOnly` требует всех шести живых сценариев и очистки.

## Границы результата

Даже успешный прогон не подтверждает полный режим приложения: здесь нет default-route TUN, elevated IPC агента, внешнего прокси, DNS/IPv6 leakage, UDP, sleep/wake или смены сети. Для отрицательных случаев проверяется отсутствие echo и трафика на шлюзах; отказ Block не различается по типу TCP-ошибки от недоступности Direct-цели. Успешные Direct-соединения других приложений и отказ внешнего upstream требуют отдельной приёмки по `network-design.md`.

Исходники закреплённого движка: [Windows TUN и DNS](https://github.com/SagerNet/sing-tun/blob/v0.7.3/tun_windows.go), [явные route ranges](https://github.com/SagerNet/sing-tun/blob/v0.7.3/tun_rules.go), [опции TUN sing-box 1.12.12](https://github.com/SagerNet/sing-box/blob/v1.12.12/option/tun.go).

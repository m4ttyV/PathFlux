# Технический аудит сетевого ядра — 24 октября 2026

Цель: подтвердить реальную выборочную маршрутизацию TCP, совместимость с локальным Docker SOCKS5/OpenVPN и восстановление сети; подготовить UDP без включения в пользовательских правилах. Предыдущие отчёты описывают историческое состояние. Этот документ обновляет их выводы, не отменяя неподтверждённых ограничений.

## Область проверки

Windows 11 Pro, build 26300, .NET 10, официальный sing-box 1.14.3. Дополнительно живой узкий TCP TUN проверен на минимальном sing-box 1.12.2. Существующий Windows OpenVPN с двумя /1 маршрутами не отключался. Docker vpn-proxy публикует 127.0.0.1:1080/tcp; внутри работают sockd и openvpn. Контейнер и его VPN-конфигурация не изменялись.

Проверялись компилятор правил, запуск и остановка движка, UAC/IPC настоящего агента, TUN mixed/gVisor, сетевые снимки, TCP/TLS через наблюдаемый SOCKS-шлюз к Docker, экспериментальные UDP-датаграммы через TUN и RFC1928 relay. Пароли и реальные пользовательские правила в тестовые конфигурации не копировались.

### Доказательство дефекта маршрутов

В неудачном production-прогоне selected TLS=1 и control TLS=1, но Docker forwards=0. Во время TUN присутствовал только новый /0 через TUN, а исходные OpenVPN /1 оставались более специфичными. После добавления явных /1 выбранный процесс стал проходить через наблюдаемый SOCKS-шлюз. Поэтому успешный check, наличие TUN и даже успешный HTTPS-запрос не являются доказательством selective routing.

Поведение default ranges подтверждено [исходником sing-tun используемой версии](https://github.com/SagerNet/sing-tun/blob/bca4bf029237/tun_rules.go). Совпадение префикса /1 здесь выбирается по более низкой метрике TUN; это проверено на текущем OpenVPN, но не является универсальной гарантией совместимости с любым сторонним VPN/WFP-фильтром или более специфичным маршрутом.

## Подготовленный UDP-тракт

Внутренняя ветка генератора разрешает SOCKS5 UDP только для NetworkLab, сохраняя порядок правил и Block. Публичный GenerateAsync всегда отклоняет Proxy UDP и оставляет SOCKS outbound network=tcp; schema1 и AgentRequest не получили переключателя UDP. Лабораторная ветка для HTTP/HTTPS UDP по-прежнему выдаёт Reject. Повторная генерация production-конфигурации после экспериментальной даёт тот же JSON.

Пробы используют отдельные процессы, прямые UDP-сокеты, случайные 64-байтовые запросы, проверку источника и независимый echo. Relay проверяет source/port и удерживает TCP lifetime. Положительные path/name подтверждены счётчиками relay/echo. В ProductionReject было 0 ASSOCIATE и 0 echo-пакетов. При REP=7 и закрытии control TCP успешных ответов не было. При FRAG=1 в sing-box 1.14.3 получили 3/3 ответа, хотя ожидалось 0: suite завершился ошибкой, результат не скрыт.

Перед включением необходимы либо исправление/проверка внешнего UDP parser, либо отдельный строгий transport guard, а затем повторные TUN-тесты. Для Docker дополнительно нужен достижимый UDP relay с корректным BND.ADDR/BND.PORT и публикацией/маршрутизацией нужных UDP-портов. Текущая ассоциация успешна, но это не доказательство передачи. Требования lifetime и FRAG: [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928.html).

## Неподтверждённое и оставшиеся риски

- Windows 10, другие Windows builds, другие VPN/WFP-продукты, Wi-Fi/cellular, смена сети, sleep/wake и reboot recovery.
- Полный IPv6 dataplane, DNS leakage и сравнение внешнего egress IP Direct с маршрутом через уже работающий Windows VPN. Восстановление таблиц после остановки проверено; идентичность egress-пути во время TUN из него не следует.
- Атрибуция очень коротких процессов и поведение при ошибке поиска процесса. Default Direct означает риск обхода при несопоставленном процессе; точный PID/потомки не поддерживаются.
- Более специфичные сторонние маршруты могут обходить default-like TUN. Поддержка LAN-потоков при BypassLan=false отдельно не подтверждена; loopback и служебные DNS остаются явными исключениями.
- Реальная гибель процесса UI/агента не подменяется тестом закрытия job. Системного fail-closed после удаления TUN нет; нужен отдельный kill switch/WFP-проект.
- Внешние HTTP/HTTPS CONNECT, продолжительный QUIC/Discord voice, MTU/фрагментация и NAT rebinding UDP не приняты.

Код сравнения снимков намеренно консервативен: стороннее изменение сети во время сессии тоже даёт неопределённое восстановление. Оно не исправляется автоматическим reset. Пользователь может проверить и архивировать журнал только при совпадении baseline.

Команды воспроизведения: [NetworkLab](tun-lab.md). Статусы TCP/process_name/process_path теперь Partial, а не полное Implemented; UDP/PID/kill switch остаются Unsupported.
